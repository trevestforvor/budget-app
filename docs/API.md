# Budget API contract (v1)

The iPhone app is a thin client. It calls these endpoints on the Budget API (`Server/`, Swift + Hummingbird 2) running on the Olares, at its public API entrance (no VPN; a bearer token on every `/v1` route). Swift wire models: `Packages/BudgetCore/Sources/BudgetKit/Models/Models.swift`. Client: `RemoteBudgetAPI`. The server and the demo run the same engine (`LedgerBudgetAPI` over `Ledger`), so the demo's behavior is the server's. Running and deploying it: [SERVER.md](SERVER.md).

Conventions: JSON; dates are ISO-8601; money is `{"minor": 123456, "currency": "USD"}` (integer minor units, never floats). Negative amounts are money out.

**Auth.** Every `/v1` route needs `Authorization: Bearer <BUDGET_API_TOKEN>` (401 without it). Writes (anything but GET) that carry an `Origin` header must come from `BUDGET_ALLOWED_ORIGINS`, or they're refused with 403 — a browser page can't drive the API with a stolen tab. `GET /health` is open and answers `{"status":"ok","version":…}` once the ledger has loaded.

**Errors** are `{"error": "<message>"}`: 400 malformed body, 401 no or wrong token, 403 cross-origin write, 404 unknown id, 413 a body too big for the route ("That's too much to send at once."; `/dash/models/save`, `use`, `remove` and `test` take up to 64 KB), 422 a valid request the ledger refused (unknown category, unconfigured provider — the message says why; `RemoteBudgetAPI` surfaces it as `BudgetAPIError.rejected`), 502 an upstream (model or provider) was unreachable, 500 anything else (logged on the server; unparseable CSV/OFX is a 422).

### Morning summary (server 0.4.0)

Yesterday's spending as a notification, at 9:30 in whatever time zone the phone last reported, so it follows a trip. The server sends it through APNs (token auth: the `apnsKey`, `apnsKeyID`, `apnsTeamID` and `apnsTopic` settings) and checks every minute who is due. A phone is due from its time for three hours, once per local date, and a failed send is retried after 15 minutes. If the last sync is more than two hours old, it syncs first. Each day's summary is saved (the last 14) and reused while its figures hold, so the model writes a day once.

|---|---|---|---|
| POST | `/v1/devices` | `DeviceRegistration {token, environment: sandbox\|production, timeZone, enabled, hour, minute}` | `DeviceStatus {enabled, timeZone, hour, minute, lastSentDay?, lastError?, pushConfigured}`. Turns the summary on or off for this token, and records where the phone is now. The app sends it on turning the summary on, whenever it comes forward, when the clock's zone changes and on background refresh. `pushConfigured` is false until the server has an APNs key. A token APNs rejects as gone (410, `Unregistered`) turns the device off. A `BadDeviceToken` is retried once on the other environment, and the device keeps the one that worked. 422 for a bad token, zone or time |
| POST | `/v1/devices/test` | `{token}` | `DeviceStatus`: yesterday's summary (in the device's zone) sent now, without marking the day as sent. 404 for an unknown token; 422 with the reason when it couldn't be sent (no APNs key, APNs refused it) |

Fields: `spent` (bills included, net of refunds), `everydaySpent`, `typicalDay` (everyday spending averaged over the 28 days before, nil under a week of history), `count`, `pendingCount`, `places` (at most three merchants, each net of its refunds), `facts` (`pace` against a typical day, `firstTime` at a merchant no earlier row shares a first word with once the ledger reaches back 90 days, `bills` and subscriptions in it, `safeToSpend` for the rest of the month, `pending`; from server 0.5.0 a `bills` fact also says when a card bill is due within three days of the morning it's sent, or past due, with what's left of its statement), and `summary`. ### Pace alerts (server 0.5.0)

A notification when this month is running ahead of what the person set: the everyday budget on pace to finish over, or a category target or merchant cap 80% used or on pace to finish over. The same push path as the morning summary (one APNs provider token shared by both). The server checks every 10 minutes and sends only during the phone's daytime, 9:00 to 21:00 in the zone it last reported; an alert that comes due at night waits for the morning, and goes only if it still holds then. Each target alerts at most once per threshold per month, and a higher threshold covers the lower one ("on pace to go over" sent means "80% used" for the same target doesn't follow). What went out is saved in `budget_settings` (`paceAlertsSent`: phone token → `"2026-10|category:dining:used80"`, this month and last), so a restart doesn't resend. At most 3 go to one phone per check; the rest follow on the next.

The math (`Ledger.paceAlerts`, all in the ledger): the everyday budget and its spending are safe to spend's (`flexBudget`); a category is its own bucket's total net of refunds as the Spending tab and checkup count it, against its target; a cap is the merchant's charges this month (`merchantCaps` in `SpendingSummary`). The pace is the month so far spread over the whole month (`spent ÷ day × days in month`), from day 8 on; before that only what's already spent can alert. "On pace to finish over" needs the projection past the limit by $10 or 2% of it, whichever is more; already over by $1 always counts. The everyday budget alerts only on its pace, never at 80%. A target in Bills or Subscriptions lands once, so it alerts only once it's over.

|---|---|---|---|

Each `PaceAlert {kind: everyday\|category\|merchant, threshold: used80\|projectedOver, targetID, name, status, title, body, link}` is past a threshold now, most pressing first; `projectedOver` also means already over. `title` and `body` are the notification's words ("Everyday is on pace to finish about $220 over. $14/day keeps you on budget."); `link` is a checkup link (`budget`, `category` + id, `merchant` + name). A kind or threshold this build doesn't know decodes as `unknown`. Ask reads the same through `checkPace` |

Absent fields read as everyday on, categories and merchants off. A registration without `paceAlerts` leaves the stored choice as it is; a phone that never sent one (an app before 0.5.0) gets none. `enabled` stays the morning summary alone, so a phone can have pace alerts with the summary off. The notification's payload carries `kind: "pace"`, `month` ("2026-10") and what a tap opens: `to: "budget"` (Spending's month), or `to: "category"` / `"merchant"` with `id` (the category id or merchant name). It's grouped with the other pace alerts (`thread-id` `pace-alerts`) and replaces an earlier one for the same target that month.

The morning summary and pace alerts are separate notifications (`collapse-id` `summary-<day>` and `pace-<month>-<target>`, threads `morning-summary` and `pace-alerts`) and never stand in for each other: the summary tells yesterday (and safe to spend) once a day, and a pace alert goes out once per target and threshold a month whatever the summary said. Both write the same phone list (`budget_settings` "devices"), one write at a time, so a pace alert dropping a dead token can't undo the summary marking a day sent (which would send it twice).

### Dashboard (second listener, `DASHBOARD_PORT`)

The browser dashboard is served on its own listener, behind an Olares `private` entrance, so the person has already signed in to Olares. It takes no bearer token. Its writes (anything but GET) must carry `X-Budget-Dashboard: 1` (a cross-site page can't send it without a preflight this server never approves) and, when the browser sends an `Origin`, come from the dashboard's own host; otherwise 403. Every `/v1` route above is also available here under the same rules. The phone's listener serves none of these.

|---|---|---|---|

### Models (server 0.5.1)

Each job keeps several models and uses the one picked: `chat` (Ask, planning and the morning summary: an OpenAI-compatible server, an optional key and a model name) and `decision` (categorizing's local server: `/v1/systemone` at an address, with an optional key; the model is always `clef`). Which provider categorizes is still the decision policy (`POST /v1/actions` `updateDecisionPolicy`); the decision pick says which server `localDecide` uses. How they're stored, imported from 0.5.0 and mirrored for a rollback: [SERVER.md](SERVER.md#models-server-051).

`ModelList` never carries a key, sealed or opened: `{chat: [Entry], decision: [Entry], chatInUse, decisionInUse, chatServer: {address?, local}, jev: {hasKey, keyUnreadable, zeroRetention, keyOrigin: default|environment|dashboard}, sealingAvailable, limit}`.
- Each list starts with the entry from the install settings (id `environment`) when there is one, then the saved models in the order they were added. Off, Jev and the chat model's server aren't entries.
- `chatInUse` is a saved id, `environment` or `off`; `decisionInUse` a saved id, `environment` or `chat`. With no pick saved, or a pick since removed, chat uses `environment` when it exists, else `off`; decision uses `environment` when it exists, else `chat`.
- `chatServer` is where `chat` points: the chat model in use's address, and whether it's local. Categorizing there sends the chat model's key, or `DECISION_API_KEY` in 0.5.0's pairing ([SERVER.md](SERVER.md#models-server-051), Keys).
- `limit` is 20 saved models per job.

`Entry {id, kind: chat|decision, name, address?, model?, hasKey, keyUnreadable, origin: dashboard|environment, inherits, local}`:
- `address` and `model` are as resolved. `address` is nil when the install settings no longer set a value the entry follows; the entry then works as Off for its job.
- `hasKey` when its key resolves and opens. `keyUnreadable` when a saved key no longer opens (`BUDGET_TOKEN_KEY` changed).
- `inherits` lists the fields (`address`, `key`, `model`) that follow the install settings rather than a saved value: all three for `environment`, some on a model imported from 0.5.0, none on one added on the dashboard. Typing a value for a field on save stops it following.
- `local` when the host is on this network: loopback, a private, link-local or 100.64/10 address, a single-label name, `.localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, or `*.olares.com` / `*.olares.cn`. The dashboard marks the rest "In the cloud".

**Saving** (`/dash/models/save`), each refusal a 422 that says why:
- The address is http or https with a host, a port (if any) from 1 to 65535, no user, password, query or fragment, at most 2,000 characters. It's saved as the server's base: a trailing `/v1`, `/v1/chat/completions` or `/v1/systemone` is dropped. It's required unless the entry inherits it and none is typed.
- A chat model needs a model name (at most 200 characters), unless it inherits one. The name (at most 60) defaults to the model name for chat and the host for a categorizing server.
- A non-empty `apiKey` (at most 8 KB) is sealed with `BUDGET_TOKEN_KEY`; without that key on the server, keys can't be saved (`sealingAvailable` is false).
- An entry's key only goes to its own server. Change the address to another server (scheme, host or port) while it has a key, and the save is refused ("The address is on another server now: type its API key, or remove the key.") until you type that server's key or send `removeKey: true`. `/dash/models/names` and a Test draft follow the same rule: a blank key uses the entry's only on the entry's own server, and `removeKey: true` sends none.
- An `id` that comes from the install settings can't be edited or removed here ("That one comes from the install settings; change it there."), and a 21st model for one job is refused.
- A new chat model is put in use only when no chat model is picked (an explicit Off counts as a pick), the install settings set none, no other chat model is saved, and categorizing isn't running on the chat model's server. A categorizing server is never put in use on its own.

**Removing** the model in use is refused ("In use. Pick another one and save first."). A categorizing server counts as in use only while the policy's provider is `localDecide`; removing the picked one otherwise puts categorizing back on its default.

**Testing** a `draft` with an `id` starts from that entry, looked up in the draft's own kind. A Jev draft's blank key uses the saved OpenRouter key, and its address is ignored.

The dashboard can answer while the server is still starting. A settings or model write that comes before the server starts reading its settings is refused with 503 ("The server is still starting. Try again in a moment."), and one that comes while they're being read waits for that. If they couldn't be read, every write is refused with 503 ("Server settings didn't load, so nothing was changed. Restart the server; its log says why.") and nothing is saved.

### Reconnecting a bank

A connection the bank ended (Plaid `ITEM_LOGIN_REQUIRED`, a 401 or 403) is marked `needsReauth`; the scheduled sync and `POST /v1/sync` leave it out, `Overview.attention` and the checkup lead with it, and the phone points to the dashboard (`ServerStatus.dashboardURL`). Reconnecting keeps the link, its accounts and its history — re-linking from scratch would make a second Item with new account ids and duplicate up to two years of rows.

- **Plaid (update mode):** `POST /v1/links/plaid/token {linkID}` → open Plaid Link with that token → when Link reports success, `POST /v1/links/{linkID}/sync`. There's no public token to exchange: the Item is the same one. The sync marks it `connected` and brings in what was missed.

The dashboard reaches these on its own listener like the other link routes (writes carry `X-Budget-Dashboard: 1`). Link ids are always `<provider>-<id>`, so `/v1/links/{id}/…` never meets the static `/v1/links/plaid/…` and `/v1/links/simplefin` routes.

### Upcoming and card bills

`Upcoming` (`GET /v1/upcoming`, server 0.5.0) is worked out by the ledger:

- `items`: `UpcomingItem {id, kind: income|bill|subscription|cardBill, date, title, amount, categoryID?, accountID?, cadence?, isEstimate, isLate?, minimumPayment?}`, soonest first; on one day income, then card bills, bills and subscriptions, each by size. `amount` is signed the ledger's way (money in positive). `date` is the start of the day in the ledger's time zone. A kind a later server adds decodes as `bill`.
  - **Income** comes from the paydays `recentPaychecks` reads (Income of $100 or more in the last 120 days, deposits within three days summed): every week or every two weeks keeps its step; twice a month and monthly keep each payday's usual day of the month, moved to the Friday before when it falls on a weekend. The amount is the median of the last four paychecks, the title the payer on the latest one. A payday up to four days late shows on today with `isLate`; later than that it's left out. Pay that stopped (no paycheck for two paydays and four days) predicts nothing.
  - **Bills and subscriptions** are the active ones on the recurring list (`/v1/subscriptions`), at their latest amount from their next expected charge, then a weekly one each week and the rest on the last charge's day of the month (every 1, 3 or 12 months); one that's late but not yet missed shows on today with `isLate`.
  - **Card bills** are what's left of each card's statement balance on its due date (past due ones on today with `isLate`), with `minimumPayment`; `isEstimate` is false.
- `byDay`: `UpcomingDay {date, totals, itemIDs}` for each day with something on it.
- `totals` (the window) and `nextSevenDays`: `UpcomingTotals {income, bills, subscriptions, cardBills}`, magnitudes. Card bills pay for spending already made (a subscription charged to a card is counted on its day and again inside a later card bill), so they're never added to bills and subscriptions.
- `nextPaycheck` (even when it's past the window) and `payCadence` ("every 2 weeks", "twice a month"); nil when no regular pay shows.
- `cardBills`: every card with a statement from its issuer, paid ones included: `CardBill {accountID, statementBalance?, statementDate?, minimumPayment?, dueDate?, isOverdue?, lastPaymentAmount?, lastPaymentDate?, purchaseAPR?, updatedAt, accountName?, paidSinceStatement?, remaining?, status?: due|paid|overdue|nothingDue}`. The ledger reads each against the card's own rows: payments into the card after the statement day (moves between accounts or payment descriptors, pending ones included), or the issuer's last payment when it's later and larger. `remaining` never goes below zero; `overdue` is the issuer's flag or a due date passed with a balance left. A statement the issuer hasn't confirmed in 35 days (card bills turned off, a broken connection) is left out. A status a later server adds decodes as `due`.

**Card bills come from Plaid Liabilities** and are off until the dashboard's "Card bills (Plaid Liabilities)" setting (`BUDGET_PLAID_LIABILITIES`) is on, because Plaid bills Liabilities per Item once it's used. With it on, after a Plaid Item's transactions sync the server calls `/liabilities/get` for its credit cards (Plaid type `credit`; an Item with none isn't asked), at most once a day per Item, and stores each card's statement in `LedgerState.cardBills` (a `budget_docs` key; a ledger saved before has none). It's best effort: whatever Plaid answers, the sync stands. The answer is kept on the link (`LinkSummary.cardBills.access`), by Plaid's `error_code`, never its message: `ok`; `needsConsent` (`ADDITIONAL_CONSENT_REQUIRED`: the Item was linked before liabilities was consented); `notSupported` (`PRODUCTS_NOT_SUPPORTED`, `INVALID_PRODUCT`); `noCreditAccounts` (`NO_LIABILITY_ACCOUNTS`, or no card among its accounts); `notReady` (`PRODUCT_NOT_READY`); `failed` (anything else; `message` says what Plaid said). Each is asked again a day later, except that a person's own sync of the link asks at once when it was `needsConsent` or `notReady`. The server logs Plaid's `request_id`, never a token.

For `needsConsent` the dashboard's Accounts page offers **Grant card-bill access**, and only that click starts it: `POST /v1/links/plaid/token {linkID, grantCardBills: true}` makes an update-mode Link token for the same Item (its access token, `products: []`, `additional_consented_products: ["liabilities"]`, the redirect URI kept) → Plaid Link → on success `POST /v1/links/{linkID}/sync`, which asks again. Nothing is exchanged, removed or relinked: the Item and its access token stay the same. New links consent to liabilities from the start.

The morning summary adds a `bills` fact for a card due within three days or past due. Ask reads all of this with the `findUpcoming` tool.

### Institutions

`ServerStatus.institutions` lists each link, then one entry per institution whose accounts all come from imported statements. `InstitutionLink` carries `lastSync` (the provider's last successful sync), `lastError` (the latest failure in the provider's words, nil once one succeeds), `accountIDs` (the `Overview.accounts` it holds, so clients join without matching names: a link holds the accounts at its institution that its provider brought in; a SimpleFIN link, one bridge for many banks, holds every SimpleFIN account) and `coversThrough` (the newest row on those accounts). A statement-only institution has `id` `statements-<name>`, `primary: fileImport`, status `connected` (nothing to sign in to) and no `lastSync`. `priority` is only in the demo's institution plan now; older servers sent `core` for every link, and it still decodes.

Every sync and import is one batch: rows are deduplicated by provider id, then fuzzily across sources (account, ±3 days, amount, descriptor), and categorized: your rules → matched transfers between your accounts → what a statement says a row is → merchant memory → the decision model once per unique descriptor → review. `Categorization.tier` says which: `rule` (with `decidedBy` "rule:<id>", readable as `Categorization.ruleID` — not text to show), `transferMatch` (`decidedBy` names the other account), `statement`, `merchantMemory`, `decisionModel`, or `user` for your own answers. Rows filed before `transferMatch` and `statement` existed said `rule`; loading a ledger gives them their tier and traces rows a rule filed to that rule.

**Money in on a credit card is never pay.** Merchant memory, a statement (an interest row) and the decision model — at ingest, when the queue is re-checked and in `/dash/recheck-filed` — never file money coming in on an account of kind `credit` under Income, and never offer Income for it (not even as the bank's hint). Such a row goes to review with honest suggestions instead: Transfer first when it reads as a payment to the card ("AUTOMATIC PAYMENT - THANK"), otherwise the spending categories it most likely refunds (how earlier charges from the same merchant were filed), then the bank's label and the model's ranking; Transfer alone when there's nothing to go on. The review reason says why ("The decision model called this income, but money coming in on a credit card isn't pay: it's a payment to the card, a refund or a statement credit."). The decision model's answer for card money in is asked apart from money in elsewhere under the same descriptor. A money-in category you made (card rewards) is fine on a card, and your own answers and your rules always win: a rule can file card money in as Income, and so can you. The first time a ledger loads on a server with this guard, rows it would have stopped (money in, credit account, Income, filed by anything but you or a rule, not hidden) go back to review the same way, with the reason "It was filed as Income, but …"; `LedgerState.upgrades` records that it ran (`card-money-in-is-not-income`), so it never runs again, and the server writes it back once.

### Transactions

`LedgerTransaction` also carries `isHidden` (default false), `note`, `transferPeerID` (the other side of a matched move between your own accounts, set on both rows), `originalMerchant` (the bank's name, kept when the merchant was renamed), `isYearly` (your say on whether it's spread over the year; unset leaves it to Budget) and `tags` (server 0.5.0: your own labels, like a trip, a project or what work pays back, in the order given; absent when there are none, never empty). From server 0.5.0 a row may also carry `orderMatch {store, orderID, shipment?, items, orderedAt?}`: what a store order it paid for bought, from an imported order history ([`/v1/imports/amazon`](#accounts-sync-and-imports-server-only)); search (`q`) matches its item names. Rows the API hands out also carry `countsAsYearly: true` when the budget spreads them — your say, a charge in a yearly series (found by the recurring search, or a merchant you said repeats yearly), or one whose description says annual ("ANNUAL MEMBERSHIP FEE"; not "semi-annual"); it's never stored. Rows cached or stored before these existed decode with them unset.

**Hidden rows** are left out of every total: spending, income, categories, merchant caps, flex and safe to spend, savings, recurring charges, insights, the checkup (which notes how many are hidden this month), the assistant's totals, and the pace the Plan projection runs at. Balances still include them. Hiding a row takes it out of review. `LedgerTransaction.isCounted(category:)` says whether a row counts (false for hidden rows and transfers; true for spending and money in); clients dim the rest with it.

**Filter** (`TransactionFilter.queryItems`, read back by `TransactionFilter(queryItems:)`; unknown names are ignored, unreadable values are a 400 saying which, an unknown period is a 422):

| Item | Meaning |
|---|---|
| `q` | Merchant, bank descriptor, note, a tag, or an amount (`42.50` exact, `42` for $42.00–42.99) |
| `category`, `account`, `tag` | Repeat for several; any of them. Tags match without case (server 0.5.0; an older server ignores `tag`) |
| `period` | `this_month`, `last_month`, `last_30_days`, `last_90_days`, `last_6_months`, `year_to_date`, `last_year` (the previous calendar year), `all`, `2026-09`, `2026-Q3` |
| `since`, `until` | ISO-8601 instants, or a day (`2026-09-01`, start of that day in the ledger's time zone). `since` is inclusive, `until` exclusive |
| `direction` | `out` or `in` |
| `min`, `max` | Bounds on the size of the amount, e.g. `25` or `25.50` |
| `needsReview`, `pending`, `modelFiled` | `true` keeps only rows in review, pending, or filed by the decision model on its own |
| `visibility` | `all` (default), `counted`, `notCounted` (transfers and hidden rows) |
| `sort` | `newest` (default), `oldest`, `largest` |
| `limit`, `offset` | Page size (default 200, at most 5000) and rows to skip for the next page |

**Edits** go through `/v1/actions` as `{"type": "editTransactions", transactionIDs, categoryID?, acceptGuess?, isHidden?, isYearly?, note?, merchant?, renameSimilar?, addTags?, removeTags?, fileSimilar?}`. `isYearly: true` spreads the rows over the year: they keep their category and bucket, but the budget counts a twelfth of each a month for twelve months instead of all in its month; `false` counts them in their month, whatever Budget found (server 0.3.0). `acceptGuess` keeps each row's current category as your answer. An empty `note` removes it. `merchant` renames the rows; with `renameSimilar` it also renames every row with the same bank descriptor and names new ones as they arrive (not for generic descriptors), and a merchant cap moves to the new name when every row under the old one was renamed. The assistant can propose this action like any write tool.

**Tags** (server 0.5.0). `addTags` puts tags on every row and `removeTags` takes them off (case ignored). A tag is trimmed, its inner spaces collapsed and a leading `#` dropped; it takes the spelling a row already uses ("austin trip" becomes "Austin trip"). At most 32 characters a tag and 10 tags a row; adding and removing the same tag, or a row past 10, is a 422. The undo puts each row's tags back; an undo built by an older server says nothing about tags and leaves them as they are. An older server drops both fields without a word (or refuses an edit with nothing else in it), so the app checks the server's version first (`ServerStatus.tagsSince`).

**Filing similar rows** (server 0.5.0, `ServerStatus.fileSimilarSince`). With `categoryID`, `fileSimilar: true` also files every other row with the same merchant or the same bank descriptor (numbers ignored, as merchant memory reads it) going the same way (money out or in) under the category, as your answer. Filing money out under a spending category also takes that merchant's refunds filed under spending, so each category stays net of its own refunds; money in under a money-in category never follows a purchase. It leaves alone rows you filed yourself (the preview's `detail` says how many), rows already filed there and settled, a matched transfer unless the category is Transfer, and anything behind a descriptor that names no merchant ("Withdrawal") or a payment app (Venmo, Zelle, Cash App, PayPal). The preview's `matchCount` counts every row it files (the chosen ones too) and `changeCount` the ones that change category; one undo puts them all back. An older server files only the chosen rows, so its preview reaches no more.

**CSV export** (`/v1/transactions/export.csv`, server 0.5.0). Columns: `Date` (the day, in the ledger's time zone), `Merchant`, `Description` (the bank's), `Amount` (signed, two decimals, no currency sign: `-42.50`), `Category` (`Uncategorized` when unfiled), `Bucket` (`Bills`, `Subscriptions` or `Everyday` for spending, a recurring charge counting as its series' kind; `Money in`; `Transfer`; empty while unfiled), `Account` (`Gold Card ••1008`), `Tags` (joined with `; `), `Note`, `Status` (`Pending` or `Posted`) and `Hidden` (`Yes` or `No`). The file starts with a UTF-8 byte order mark (so Excel reads it as UTF-8 rather than the system's legacy encoding). RFC 4180: a header row, CRLF after every record, a field quoted when it holds a comma, a double quote or a line break, a quote inside doubled. Text that starts with `=`, `+`, `-`, `@`, a tab or a CR gets a leading `'`, so a spreadsheet never runs a merchant name or a note as a formula. Hidden rows and transfers are included (the `Hidden` and `Bucket` columns say which).

**Pending to posted.** When Plaid posts a pending charge under a new id (`pending_transaction_id`), the posted row keeps what you did to the pending one: hidden, the note, its tags, a renamed merchant, your category, and its transfer pair. Removing an imported row that a sync also brought in carries its tags onto the synced row the same way.

### Rules

A rule files rows matching `RuleMatch {merchantContains?, descriptorContains?, direction?: out|in, minAmount?, maxAmount?, accountID?}` under a category. Every condition given must hold; it needs text or an account. Text ignores case, numbers, spaces and punctuation ("PARAMOUNT PAYROLL" catches "PARAMOUNT PAYROLL 0923 PPD"; "Google Fi" catches "GOOGLE*FI 4DFLFD" and "GOOGLE *FI AB12CD"). Amounts are sizes (`"1000"`), both inclusive. A rule filing under a money-in category (Income, card rewards) only ever takes money coming in: one asking for money out is refused ("Money going out is never income.", or "Money going out never counts as money in, so a rule can't file it under Card rewards."), and one that says either way is saved as `direction: "in"` so it reads that way everywhere; rules stored before this never file money going out as money in either. Turning a rule off or on leaves its conditions as saved. When several rules match a row, the newest that's on and whose category is live wins; rules run before everything else at ingest.

`BudgetRule {id, match, categoryID, createdAt?, createdBy: person|assistant, isEnabled}`. Rules saved before they had ids load as `rule-1`, `rule-2`… by position, credited to the assistant (applying an Ask proposal was the only way to make one), and keep those ids when next saved.

`GET /v1/rules` returns `RuleSummary {rule, matchDescription, hitCount, matchCount, conflicts, isDead}`: `matchDescription` reads like "Bank description contains “PARAMOUNT” · money in · $1,000 or more · Total Checking ••0909"; `hitCount` is the rows it filed that are still filed that way; `matchCount` the rows it matches now; `conflicts` the other rules that are on and disagree with it (a different category, and a row they both match or exactly the same conditions), newest first; `isDead` means its category was merged away or is gone, so it files nothing.

Writes, through `/v1/actions`:
- `{"type": "createBudgetRule", match, categoryID, applyToExisting}` makes a rule; with `applyToExisting` it also files every row it wins (a newer rule matching the same row keeps it), taking them out of review — never a row the person filed themselves. The preview's `changeCount` is what saving files (rows that move, and rows waiting for review that leave it); its detail says how many of your own answers keep their category. A new rule's id is never one a deleted rule's rows still carry. The assistant's proposals carry `createdBy: "assistant"`. Servers from 0.2.0 keep a rule's `direction`, amounts and `accountID`; the app refuses to send such a rule to an older one, which would drop them.
- `{"type": "updateBudgetRule", ruleID, match?, categoryID?, isEnabled?, applyToExisting?}` replaces what's given (`match` as a whole). A rule that's off can't re-file.
- `{"type": "deleteBudgetRule", ruleID}` removes it. Rows it filed keep their category, as they do when it's turned off.

Unknown rule ids are a 404.

### Categories

`BudgetCategory` carries `kind`: `spending` or `moneyIn`. Money in counts like income — Income itself, and categories you make for it, like "Card rewards" for statement credits, offers and points back. Every income figure counts it (`Overview.monthIncome`, `TransactionSummary.income`, cash flow's `MonthFlow.income`, expected income in the flex budget, savings capacity and guidance, the checkup, the assistant's `cashFlow`, `savingsCapacity` and `queryTransactions`, whose rows in one are marked `moneyIn`) and no spending figure does: a money-in category is never in a spending total, category tile, budget group or the flex math, has `countsAsSpending: false` always, no target and no budget type (`group` is kept but means nothing), and no spending history (422). `sumByCategory` returns what one received (`received`, not `total`), and lists every money-in category's receipts beside the spending categories (`moneyIn`). Money going out is never filed under a money-in category by a rule, merchant memory, the model or a review fan-out, and never offered one as a suggestion. Transfer stays the one category that's neither (`kind: spending`, `countsAsSpending: false`). Categories stored or cached before kinds decode as `moneyIn` for `income` and `spending` otherwise; the kind is set when a category is made and never changes.

`BudgetCategory` also carries `color` (a `CategoryColor` name: `iris`, `lilac`, `orchid`, `azure`, `cyan`, `irisDeep`, `amber`, `coral`, `rose`, `teal`, `lime`, `violet` — the DesignSystem `DSTone` names, never hex) and `isArchived` (with `mergedInto`, the category it was merged into, so an undo made before the merge files its rows there). Categories cached or stored before these decode with no color and not archived. `effectiveColor` is its color, else the standard one for the id (health rose, travel teal, fees coral, utilities lime, transfer violet; the rest as before), else amber.

- `{"type": "createCategory", name, symbol?, monthlyTarget?, group?: bills|subscriptions|everyday (older fixed / flexible / nonMonthly are read as bills / everyday / everyday), color?, kind?: spending|moneyIn}`. `kind` defaults to `spending`. Without a color it gets the one the other live categories wear least. A name that matches a merged-away standard category brings that one back (as the kind it was; asking for the other kind is refused). A money-in category goes after Income in the list, ignores `group`, and refuses `monthlyTarget`; its icon defaults to `arrow.down.circle`. For example `{"type": "createCategory", "name": "Card rewards", "kind": "moneyIn", "symbol": "gift", "color": "amber"}`.
- `{"type": "updateCategory", categoryID, name?, symbol?, color?, group?}`. The id and the kind never change (a `kind` sent along is ignored; the assistant's schema refuses it). Income and Transfer take only a symbol and a color; a money-in category you made takes a name too, but no budget type ("Card rewards counts as money in, so it has no budget type."). A budget-type change previews safe to spend before and after.
- `{"type": "mergeCategory", from, into, combineTargets?}` moves `from`'s rows (each keeps how it was filed and whether it's in review), its rules and review suggestions to `into`; with `combineTargets` its monthly target is added to `into`'s, otherwise dropped. A standard category is then archived (so it isn't added back when the standard list grows); one you made is removed. Both must be the same kind — spending into spending, money in into money in (card rewards into Income) — or it's refused ("Dining is spending and Income is money in, so one can't be merged into the other."). Income is never merged away, and Transfer can't be merged either way.

An archived category still resolves by id for old rows, but nothing new is filed under it: re-filing, targets and rules refuse it, and the decision model's options, the assistant's tool schemas and prompt, and the app's pickers leave it out.

### Review settings

`DecisionPolicy` also carries three toggles, off in policies saved before them: `reviewNewMerchants` sends every new merchant to review however sure the model is (the model is only asked about descriptors with no memory, so this is everything it would file on its own, the bank-agreement shortcut included); `reviewAbove` (an amount like `"500.00"`, or absent) sends anything bigger to review when the model or merchant memory would have filed it — rules, matched transfers, statement rows and your answers still file on their own; `holdPending` leaves pending charges out of `GET /v1/review` (and the review count) until they post. Held rows keep the would-be category as their first suggestion, and the review reason says why ("More than $500. You asked to check big amounts before they're filed.").

`updateDecisionPolicy` takes `reviewNewMerchants?`, `holdPending?` and `reviewAbove?` (`"0"` turns it off). The model re-decides the waiting rows when `rerunPending` says so, or by default when the provider, threshold or escalation changes — not for the toggles alone.

### Assistant memory and chat history

Server 0.5.0 (`ServerStatus.assistantSince`); an older server answers 404 to these routes and refuses `rememberFact` as an unknown action. Not to be confused with [merchant memory](#merchant-memory).

**Assistant memory** is a short list of facts the person asked Ask to keep in mind ("Saving for a trip to Lisbon in March"), kept in the ledger (`LedgerState.assistantMemories`, so an admin reset clears it). `AssistantMemory {id, text, createdAt, updatedAt?, source?: person|assistant}`. Text is kept on one line, trimmed, at most 200 characters; a second memory with the same text (ignoring case) is a 422, and so is adding a 31st. The system prompt carries them in their own section, newest first, up to about 2,000 characters (it says how many older ones it left out). They're background, not ledger data: grounding never counts a figure in a memory, so the model can't quote one as if a tool had worked it out.

`{"type": "rememberFact", fact}` on `/v1/actions` adds one with `source: "assistant"`. It's the assistant's write tool: the model proposes it as a card and nothing is remembered until the person applies it. `POST /v1/assistant/memories` adds one as the person's.

**Chat history.** Every `/v1/ask` is kept as a turn of a conversation: `ChatSession {id, title, createdAt, updatedAt, turns: [ChatTurn {id, question, askedAt, reply: AskReply}]}`. A question without a `conversationID`, or with one the server doesn't know, starts a conversation under that id (at most 128 characters, a 422 past it; a blank one counts as none), titled from the question (cut at a word past 60 characters; PATCH renames it, up to 60). A known one continues it: the model is given the latest six turns (questions and answers, and for the two newest their tool calls and results, up to about 16,000 characters), and figures those tool results returned may be quoted again. A conversation keeps its latest 40 turns; past 50 conversations the least recently used one is deleted. Conversations are stored in Postgres (`budget_chats`, one row per conversation), outside the ledger, and an admin reset that replaces the ledger deletes them. `ChatSessionSummary {id, title, createdAt, updatedAt, turnCount, lastQuestion?}` is a conversation without its turns. Proposals in an old turn are kept as they were proposed; whether one was applied isn't recorded, so the app shows them as earlier, not to apply again. The app leaves out a proposal whose action it doesn't know (one a newer server added) rather than failing the answer or the conversation.

### Merchant memory

`GET /v1/memory` returns `RememberedMerchant {descriptor, merchant, categoryID, source, confidence?, rowCount, lastSeen}`: for each normalized descriptor with a settled answer, the category its newest settled row has, where that answer came from (`user`, `rule`, `statement`, `decisionModel`, or `merchantMemory` when every row was itself filed from memory), the model's confidence when it made the call, how many rows share the descriptor, and the newest one's date. Generic descriptors ("Withdrawal"), matched transfers and hidden rows teach it nothing.

### Recurring choices

`{"type": "setRecurring", merchant, isRecurring?, cadence?: weekly|monthly|quarterly|yearly, kind?: subscription|bill}` is your say on one merchant's recurring charges (server 0.3.0), kept in `LedgerState.recurringChoices` by lowercased merchant name. `isRecurring: false` takes it off recurring: never listed, never expected, never spread as yearly, and its charges count in their category's bucket. `true` lists it on `cadence` (without one, the cadence Budget found) as `kind` — which is also the bucket its charges count in — even from a single charge, so a first yearly charge can be marked yearly, and its charges are then spread over the year. Leaving `isRecurring` out hands the merchant back to Budget. It returns an `undo` that restores the previous choice. It isn't an assistant tool.

### Recurring review (server 0.5.0)

`GET /v1/recurring/review` (read tool `recurringReview`) returns `RecurringReview {asOf, candidates, maybeStopped, ended?}`, the questions the Recurring screen and the dashboard's Review → Recurring tab ask. Both lists hold `Subscription` items, as `/v1/subscriptions` shows them.
- `candidates` ("Is this recurring?"): a merchant's charges that look like a series that's only begun, below the recurring list's bar — two monthly charges, three weekly — or a little less regular than it allows (half the gaps near the cadence). Every charge must be within a fifth of the typical one (2% from an everyday category, so two dinners a month apart aren't asked about), at least $1, and the next charge mustn't be overdue. A merchant on the list, or one you had a say on (`setRecurring`), never is. Answer with `setRecurring`: `isRecurring: true` with the candidate's `cadence` and `amount` puts it on the list; `false` takes it off for good (it shows under `notRecurring`). Most expensive per month first.
- `maybeStopped` ("Did this stop?"): series on the list with no charge for about a cycle and a half (11 days for weekly, 46 for monthly, 137 for quarterly, 410 for yearly). The silent drop about three cycles in (`/v1/subscriptions`) stays as the fallback. Longest overdue first.
- `ended`: merchants you said stopped whose series would otherwise still be listed, so one can be put back.

`{"type": "reviewRecurring", merchant, answer?: stopped|stillActive, restores?, mark?}` answers "Did this stop?" for a merchant on the list, kept in `LedgerState.recurringReviews` by lowercased merchant name as `RecurringReviewMark {merchant, endedAt?, snoozedUntil?}`:
- `stopped` ("Yes, I canceled it") ends the series now: it leaves `/v1/subscriptions` and its totals, and its charges leave the usual month of bills or subscriptions the flex budget averages at once instead of as they age out. Its past charges keep their category and their bucket in their own months, and a past month's budget (worked out as of its end, as `/v1/budget` and the monthly recap show it) isn't rewritten. A charge after `endedAt` brings it back. The preview's effects are the usual month of its kind before and after, and the everyday budget after.
- `stillActive` ("No, still active") keeps it and doesn't ask again for one cycle (`snoozedUntil`).
- `restores: true` sets the mark exactly to `mark` (absent clears it), with no checks: the `undo` every answer returns, and how an ended series is put back.

A merchant that isn't on the list is a 422. It isn't an assistant tool; the app gates it on `ServerStatus.recurringReviewSince`.

`{"type": "forgetMerchant", descriptor}` (the entry's descriptor, or a raw one) takes a descriptor out of memory: new rows with it are decided afresh until you file one of its rows yourself, and past rows keep their category. The ledger keeps the list in `LedgerState.forgottenMerchants`. It isn't an assistant tool.

### Net worth (server 0.5.0)

| Method | Path | Returns |
|---|---|---|
| GET | `/v1/networth?range=1M\|3M\|YTD\|1Y\|ALL` | `NetWorth`: the history and today's breakdown (below). `range` defaults to `3M`, is read case-insensitively, and anything else is a 400. A server before 0.5.0 answers 404, which the app shows as not available yet |
| GET | `/v1/assets` | `[ManualAsset]`: the assets and debts kept by hand, in the order they were added |

`NetWorth {range, asOf, start, points, netWorth, assets, liabilities, change, changePercent?, assetLines, liabilityLines, manualAssets, estimatedThrough?, note?}`:
- `points: [NetWorthPoint {date, netWorth, assets, liabilities, isEstimated?}]`, oldest first, today last: every day for ranges up to about 120 days, every few days beyond (the first day and today are always there). `start` is the range's first day, or the ledger's first day (its first row, recorded balance or hand-kept value) when it holds less. Today's `netWorth` equals `Balances.netWorth`.
- **How each day is worked out.** Checking, savings and cards are walked back from today's balance through each day's rows; on a day a sync recorded the bank's balance, the walk starts again from that figure. Investments (balance-only) hold their latest recorded balance; before the first one they hold that first value (today's, with none), and those days carry `isEstimated: true`. `estimatedThrough` is the last such day and `note` says so in a sentence. Hand-kept items count from the day they were added, at each value they were given.
- `change` is today less the first point; `changePercent` is that as a percent of the first point, nil when the first point wasn't above zero.
- `assetLines` / `liabilityLines: [NetWorthLine {id, name, detail?, group, value, change?, isManual?, isEstimated?}]`: one per account (`id` is the account id) and per hand-kept item, ordered by `group` (`cash`, `investments`, `realEstate`, `vehicles`, `otherAssets`; `cards`, `loans`, `otherDebts`) then value. A debt's `value` is what's owed, positive. `change` is since `start`. A group the app doesn't know decodes as `otherAssets`.

**Recorded balances.** After each provider sync (Plaid, SimpleFIN; never a statement file, whose balance is the statement's) the server records each reported account's balance for the day in the ledger's time zone, one per account per day (a later sync that day replaces it). They live in their own Postgres table, `budget_balances` (migration 3), not in the ledger document. `/v1/admin/reset` clears them; with `seedDemo` it records the demo's two months of investment balances.

**Hand-kept assets and debts** (`LedgerState.manualAssets`): `ManualAsset {id, name, kind: asset|liability, category: realEstate|vehicle|loan|other, value, updatedAt, createdAt?, history?: [{date, value}]}`. `value` is never negative (a debt's is what's owed). They change through `POST /v1/actions`; neither is an assistant tool:
- `{"type": "saveManualAsset", name, kind?, category?, value}` adds one (`kind` defaults to `liability` for a `loan`, else `asset`; `category` to `loan` for a debt, else `other`). With `id`, only the fields given change; a new `value` is added to `history` from today (a second change the same day replaces the first). `undo` removes a new item, or puts a changed one back exactly. A blank name, a negative value or a change that changes nothing is a 422; an unknown `id` a 404.
- `{"type": "removeManualAsset", id}` removes it and its history from net worth; `undo` restores it exactly (`saveManualAsset` with `restore`).

`Balances` (in `Overview`) carries `otherAssets` and `otherDebts`, the hand-kept totals, when there are any (nil otherwise, as before).

### Home, the budget month and history

`Overview.flex` carries the budget (`expectedIncome`, `bills` and `subscriptions` — a usual month of each — planned savings, `flexNumber` the everyday budget, `flexSpent` everyday spending, safe to spend, days left after today, and `perDayLeft`: safe to spend spread over the rest of the month, today included, zero once it's gone). `expectedIncome` is the lower of `averageIncome`, the last 3 months' average, and `recentPaychecks`, a month of the latest `paycheckCount` paychecks. `incomeSource` (`threeMonthAverage` or `recentPaychecks`) says which one it is. All four were added in server 0.3.3; from an older server they're absent and the income is the average. `SpendingSummary.merchantCaps` lists merchant caps with this range's spend. See [BUDGETING.md](BUDGETING.md).

`Overview` also carries, each optional so older payloads decode:
- `attention: [DataAttention {id, kind, title, detail, institution?, accountID?}]`, worst first: `needsReauth` for each connection to sign in to again (`reauth-<link id>`); `stale` for each checking, savings or card account whose newest row is older than max(10 days, 3× the median gap between its days with rows) (`stale-<account id>`; an institution waiting for a sign-in doesn't also list its accounts); `emptyLedger` (`no-data`). The checkup's data section shows the same items.
- `balances: {cash, cardsOwed, investments, netWorth, cashAfterCards, otherAssets?, otherDebts?}`: `cash` is `cashOnHand`, `cardsOwed` the card balances as a positive amount, `netWorth` = cash − cardsOwed + investments + otherAssets − otherDebts, `cashAfterCards` = cash − cardsOwed. `otherAssets` and `otherDebts` are the [hand-kept items](#net-worth-server-050) (server 0.5.0), absent when there are none.
- `lastSevenDays: [DaySpend {date, flexibleSpent}]`, oldest first, today so far last: everyday spending by the same rules as `flex.flexSpent` (a spread charge left out of the days), each day its own net (a refund lowers its own day, never below zero).
- `lastSevenDaysSpent`: everyday spending over those seven days as one window, refunds netted across the days — the week's figure, by the same rule as safe to spend.
- `reviewDecisions`: `reviewCount` rows as the review groups one answer each files (what the phone's badge counts), and `reviewHeadline` the queue in the phone's sentence ("8 quick answers file 11 transactions."), nil when nothing waits.

Every spending figure uses one rule: each category is net of its own refunds and never below zero, and totals are the sum of the categories. A category that took in more than it spent adds nothing and never cancels another category's spending, so the month's total, the category rows, the budget groups, cash flow and safe to spend agree to the cent. Days left count today (`FlexBudget.daysLeftIncludingToday`): "5 days left" on the 26th of a 30-day month, everywhere.

`monthTarget` and `leftToBudget` are no longer sent (the flex budget is the budget); they still decode. `Insight.askPrompt` is a question for Ask that follows up on the insight; an `idle-cash` insight appears when checking holds $500 or more beyond a month and a half of essentials.

`BudgetMonth {month, isCurrent, flex, summary, groups, unallocatedFlex, everythingElseSpent, stillToCome, hasFullHistory?}` (`GET /v1/budget`):
- `flex` is the flex budget as the month stood at its end (a past month's averages the three months before it, and it has no `perDayLeft`).
- `hasFullHistory` is false when those three months aren't all in the ledger (the first months of a ledger): their "budget" counts months with no data as zero, so the app shows what was spent, not a budget or an overspend. Nil from older servers.
- `summary` is written by the ledger, never a model: for this month the checkup's own pace and safe-to-spend sentences; for a past month how it ended against the whole month before (only when the ledger covers all of that month) and what was left of the everyday budget (only with full history). The pace sentence leaves charges spread over the year out of both months.
- `groups` is bills, subscriptions and everyday, each `BudgetGroup {group, planned, spent, categories: [CategoryTotal]}`: `planned` is a usual month of bills or subscriptions, and the flex number for everyday; `categories` those with spending or a target that month. A charge lands in its merchant's recurring kind when the merchant is on the Recurring list, else in its category's group, so a category can show in two groups (a gym in Health under subscriptions). A charge spread over the year counts its twelfth in each of the twelve months from its own, listed as its category with `isYearly: true` (id `<category>-yearly`).
- `unallocatedFlex` = the flex number − the everyday targets (negative when the targets promise more); `everythingElseSpent` the everyday spending in categories with no target; `stillToCome` what a usual month of bills and subscriptions still has to come this month (zero for a past month).

`CategoryHistory {categoryID, months: [MonthSpend {month, spent, target?}], averageMonthly, monthsAveraged}` (`GET /v1/categories/{id}/history`): oldest first, this month so far last, months before the ledger's first row left out. `target` is today's target on every month (targets have no history). The average covers complete months the ledger fully covers — not this month, and not a first month the history starts partway through.

`SavingsPlan.history: [MonthFlow {month, income, spending, net, isPartial}]`: up to six complete months, then this month so far (`isPartial`). `spending` is every category's spending as it went out (a spread charge whole in its month), each net of its refunds, so the last three complete months' `net` average to `canSaveTypical` exactly. `averageCashChange` is how much checking and savings actually grew a month over the same three months (the projection's pace); the difference went to investments or card balances.

`MonthlyRecap` (`GET /v1/recap/month?month=2026-08`, read tool `monthlyRecap`; server 0.5.0): a finished month in review. Without `month`, last month; this month, a month the ledger doesn't reach, or a misspelled month is a 422.
- `income`, `spending` and `saved` (= income − spending; negative when spending ran past income) are that month's `MonthFlow`, so they match Plan's cash flow to the cent. `movedToSavings` is what went into savings accounts as transfers, as "saved first" counts it.
- `buckets: [RecapBucket {group, spent, planned?}]` are bills, subscriptions and everyday from that month's `BudgetMonth` (a spread charge counts its twelfth, so they can differ from `spending` by that). `planned` is nil when `hasBudget` is false: the month didn't have three full months before it.
- `categoryChanges: [RecapCategoryChange {categoryID, name, spent, previous, change}]`: up to three spending categories that moved $20 or more against the whole month before, biggest first; empty when the ledger doesn't cover that month.
- `cashChange` is checking and savings at the month's end less at its start. `netWorthChange` is the same for net worth, from the [net worth history](#net-worth-server-050) (`Ledger.recapNetWorthChange`): net worth at the end of the month's last day less at the end of the day before it. It's nil when the history doesn't reach the day before the month, or when either end is estimated (an investment with no balance recorded by then), and the app (and Ask) then shows `cashChange`.
- `summary` is a sentence or two from these figures, written by the ledger. `showsUntil` is the end of the first week of the next month for last month's recap (nil for any other), and `isFresh` says whether `asOf` is before it: when Home shows the card.

`navigate` also takes `month` ("2026-09", for Spending) and the `recurring` screen.

`AskReply.proposedActions` carries `ProposedAction {id, action, title, detail, effects}` for each write or client tool call the model made. Effects are computed by the ledger at proposal time. See [ASSISTANT.md](ASSISTANT.md) for tools, grounding and the decision model.

### Plan scenarios (server 0.5.0)

A scenario is a named set of changes you expect, laid over the forecast to see where cash after cards would go: "New car" with a $3,000 down payment and $450 a month from March, "Bonus and raise", "Bigger place". They're kept in `LedgerState.planScenarios` (one `budget_docs` row), at most 12, each with at most 24 changes.

`PlanScenario {id, name, events: [PlanEvent]}`; `PlanEvent {id, name, kind: income|expense, amount, startMonth: "2027-03", endMonth?, cadence: once|monthly|yearly, isEnabled}`. `amount` is always positive and `kind` says which way it goes. A `once` change happens in `startMonth` (it has no end); `monthly` every month from `startMonth` through `endMonth` (inclusive; without one it runs on); `yearly` in `startMonth` and every twelve months after, through `endMonth`. A switched-off change (`isEnabled: false`) stays in the scenario and adds nothing. An unknown `kind` reads as `expense` and an unknown `cadence` as `once`.

| Method | Path | Returns |
|---|---|---|
| GET | `/v1/scenarios?horizonMonths=12` | `ScenarioList {horizonMonths, baselineEnd, scenarios, outcomes: [{scenarioID, endBalance, effect}]}`: every scenario, and where each leaves cash after cards at the end of the horizon (default 12, 1 to 36; anything else is a 400) beside the plain forecast's `baselineEnd`. `effect` = `endBalance` − `baselineEnd` |
| GET | `/v1/scenarios/{id}` | One `PlanScenario`; 404 if it's gone |
| POST | `/v1/scenarios` `SavePlanScenario` | 201 with the new `PlanScenario`. An id in the body must be new (422 otherwise); without one the server makes one (`scn-…`) |
| PUT | `/v1/scenarios/{id}` `SavePlanScenario` | The `PlanScenario` with its name and changes replaced whole (one that isn't there is created with this id) |
| DELETE | `/v1/scenarios/{id}` | `ActionResult` with an `undo` that puts it back |

Writes are the actions `{"type": "savePlanScenario", scenarioID?, name, events?: [{id?, name, kind, amount: "450", startMonth, endMonth?, cadence, isEnabled?}]}` and `{"type": "deletePlanScenario", scenarioID}` on `/v1/actions` (and `/v1/actions/preview`), which the routes above wrap. A save replaces the scenario's name and changes whole, so switching a change off is a save with it `isEnabled: false`; a change without an id gets one (`evt-…`). The ledger refuses (422) an empty name or one another scenario has, a change with no name, an amount of zero, a month not written `YYYY-MM`, or an end before the start. Saving a new scenario returns an `undo` that deletes it; saving over one returns the scenario as it was. Neither is an assistant tool: Ask reads scenarios with `planScenarios`, projects against one with `projectBalance`'s `scenarioID`, and proposes no changes to them.

**The math.** The point `m` months out (`Projection.projected[m]`) is the plain forecast plus every switched-on change in this month and the `m − 1` after it, so this month's changes show from the first projected point and today's point never moves. The low and high band moves with it. With a scenario, `Projection` also carries `scenarioID`, `scenarioName`, `baseline` (the plain forecast's points), `baselineEndBalance` and `scenarioEffect` (`endBalance` − `baselineEndBalance`); `monthlyNet` and `history` stay the plain forecast's. A goal checked against a scenario (`GoalCheck.scenarioID`) adds the changes of every month that starts before its date (a goal on January 1 counts December's bonus, not January's raise) to what the pace sets aside; `monthlyNeeded` stays the goal over the months to it.

### Cash flow (server 0.5.0)

`GET /v1/flow?month=2026-09` (without `month`, this month so far; a month not written `YYYY-MM` or not started yet is a 422) returns `CashFlowSankey {month, isPartial, income, spending, saved, drawnFromCash, nodes, links}`, the month's money from left to right:

- **Column 0, sources:** each payer of money filed under a money-in category (`kind: income`), largest first, the four largest named and the rest as "Other income" (`other`); and "From cash" (`drawn`) when spending passed income. A payer's money taken back comes off the smallest named source, so the sources add up to `income` exactly.
- **Column 1:** Bills, Subscriptions and Everyday (`bucket`, with `group`), in that order, then "Saved" (`saved`, income left after spending) when there was some.
- **Column 2:** each bucket's categories (`category`, with `categoryID` and `group`), largest first: the four largest named and two or more others together as "Other bills" (`other`); a lone fifth is named.

`Node {id, label, kind, column, value, group?, categoryID?, color?}`; `color` is a design-system tone name (a category's own color; cyan for income, amber for cash drawn, teal for Saved, azure, violet and lilac for the buckets), nil for a bucket's "Other" node ("Other income" is cyan like the rest of income). `Link {source, target, value}`. Sources fill the buckets in order (the largest source first into Bills), so every node's inflow equals its outflow and each column adds up to `income + drawnFromCash` = `spending + saved`, to the cent.

The figures are the month's everywhere else: `income` is the cash flow's (`MonthFlow.income`); `spending` and each bucket are the budget's (`BudgetMonth.groups`), each category net of its refunds and never below zero, a charge spread over the year at a twelfth, hidden rows and transfers left out. A past month is worked out as it stood at its end, as `GET /v1/budget` does. Ask reads the same figures with `monthFlow`.

### Sync health and SimpleFIN

- **One row per bank.** A SimpleFIN link that has synced since 0.6.0 is listed in `/v1/status` `institutions` as one row per bank behind it: id `<linkID>~<12 hex>` (never SimpleFIN's own connection id), `institution` the bank's name, `accountIDs` that bank's accounts, `syncLinkID` the link, `reconnect: "providerSite"`. A bank SimpleFIN reports `con.auth` for is `status: "needsReauth"`, `errorKind: "needsSignIn"`, `failingSince`, `reconnectURL: "https://beta-bridge.simplefin.org"`; the link and its other banks stay connected. A link SimpleFIN refuses as a whole (403 or `gen.auth`) is one row, `needsReauth`, `errorKind: "revoked"`, `reconnect: "dashboard"`.
- **`POST /v1/links/:id/sync`** takes a bank's row id too and syncs its link, so an app that sends a row id back gets a 200.
- **`PUT /v1/links/:id/token`** `{setupToken}`: a new SimpleFIN setup token for an existing SimpleFIN link (its id, or one of its banks' row ids). The link keeps its id, accounts and history. Answers the sync's `LinkSyncResult` plus `note` when none of the old account ids came back ("These accounts came in as new ones; your old ones keep their history."). 422 for a link that isn't SimpleFIN's or a token SimpleFIN won't take; 400 for any other body.
- **Request budget.** Scheduled runs pull at most `simplefinDailyPulls` (default 4) times a day, spread evenly (24 ÷ that many hours apart: 6 at the default, 3 at 8); every request counts toward the hard stop of 20, so a setting near 20 leaves little room for the person's own syncs. Between scheduled pulls, the link's result is `ok` with `skipped` saying when the next pull runs. The person's syncs run until 20 requests in a rolling 24 hours; past that, `ok: false`, `errorKind: "rateLimited"`, and `error` says when the next pull can run. Each request is logged as `simplefin <linkID>: request N of 20 today (fresh|repair|backfill)`.
- **Errors.** 403 or `gen.auth` → `revoked`; 402 or `gen.api` → `providerSetup`; the budget → `rateLimited`; anything else → `transient`. `errorCode` is `http-403`, `http-402`, `gen.api`, `budget` or `http-<status>`.
- **`/v1/links` (dashboard)**: SimpleFIN links carry `banks: [{id, name, status, errorKind?, lastGoodAt?, accountIDs}]` and `requestsToday`.
- **Account health.** `Overview.accountHealth: [AccountHealth {id, state, lastGoodSync?, balanceAsOf?, staleSince?}]`, one per account. `state`: `current`; `stale` once 2 days pass without a clean pull of the account (`lastGoodSync`: `Account.lastSyncedAt`, stamped by each provider pull that brought it without a problem, never by a statement; before an account's first stamp, its link's last clean sync; for a SimpleFIN account, its bank's `balance-date` when that's older, since the Bridge can serve old data without an error), `staleSince` = last good sync + 2 days; `waitingForSignIn` for an account under an `institutions` row that's `needsReauth` (a SimpleFIN bank row pauses only its own accounts); `statementsOverdue` for a statement account whose newest row is more than 40 days old (`lastGoodSync` is that row's day); `notSynced` for an account no link brings any more, or one under a link that hasn't synced cleanly yet. Unknown states decode as `current`. `balanceAsOf` is the bank's date for the balance; nil for a statement account (an import stamps the day it ran, not the statement's). The 2 days don't scale with `syncIntervalHours`: set past about 47 hours, accounts go stale between scheduled syncs.
- **Stale in `attention`.** Each `stale` account is also a `DataAttention` with `kind: "stale"`, `reason: "syncStale"`, id `sync-stale-<account id>`, `accountID` and `linkID` (the link to sync), ahead of the quiet-account items, which now carry `reason: "quiet"` and skip an account that's stale or waiting for a sign-in. The statement threshold for a quiet item moved from 38 to 40 days, the same number as `statementsOverdue`.
- **Stale push** (`ConnectionAlertKind.accountStale`): one per institution whose accounts went stale, episode keys `stale|<accountID>|<lastGoodSync epoch s>` (the account longest unheard from first; the others ride along), so a good sync ends the episode and a restart doesn't resend. Accounts that go stale together push once, and one still stale when the first recovers doesn't push again; one that goes stale later, while the first is still stale, pushes only once the first recovers (the sender skips an alert whose first key went out and marks keys only on send). Never for an account waiting for a sign-in, nor for one from a provider with a link whose `errorKind` is `providerSetup` (that link's push covers it). Copy: "Harbor Freedom hasn't updated since Oct 12" / "Open Accounts to check its connection." No mask, no amount.

### Imports: undo and hide

`GET /v1/imports` records carry `undo: {mode: allowed | warn | refused, message?}`, worked out on every read (never stored), and `hiddenAt` (when the person hid them) only while every row the batch still has is hidden, also worked out on every read: a batch shown again, by the hide's undo or from Activity, drops it and can be hidden again. A file import is `allowed`. A Plaid sync is `refused`: its cursor has moved on, so Plaid never sends those rows again and removing them would lose them for good; hide them instead. A SimpleFIN sync is `warn`: its next sync fetches its most recent days again, so rows from then come back, and linking the connection again fetches the rest. A batch already undone, or a failed sync, is `refused`.

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/v1/imports/{batch}/undo` | — | `RollbackPlan {batchID, rows, bySource: {sourceKind: rows}, returning, verdict: undo \| undoReturns \| refuse, message}`: what Undo would do now. `returning` counts the SimpleFIN rows posted on or after the start of that link's next sync (none once the link is gone). A batch with any SimpleFIN rows is `undoReturns` even when `returning` is 0, because linking the connection again brings them back; the message says which. `refuse` whenever the record's `undo.mode` is `refused` |
| DELETE | `/v1/imports/{batch}[?acknowledge=returning]` | — | `{removed}`. 409 with the plan's message, changing nothing, when the verdict is `refuse`, or `undoReturns` without `?acknowledge=returning`. The plan is worked out inside the same ledger write as the removal, so no sync slips in between. The record is marked `rolledBack` only on success |
| POST | `/v1/imports/{batch}/hide` | — | `ActionResult` (with `undo`, an `editTransactions` that shows them again): hides the batch's rows from every total (balances keep them) and sets the record's `hiddenAt` whenever the batch's rows end up all hidden (so a batch already hidden gets marked, with no `undo`, and a batch with no rows left doesn't). A hidden row stays hidden when its provider sends it again |

**Statement ids (server 0.6.0).** No id holds an account number. An OFX or QFX row's id is `fileImport:<account id>:ofxh1-<20 hex>`, a keyed hash (HMAC-SHA256 under a key derived from `BUDGET_TOKEN_KEY`) of the id 0.5.x made, `ofx-<ACCTID>-<FITID>`; an account an older untargeted OFX import named after its number becomes `fileImport:stmt-h1-<16 hex>`. So a statement, OFX as well as CSV, needs `accountID` or `options.accountName` (a new account; an OFX and a CSV with the same institution and name share it); without either it's a 422, "Statement files need an account". The account's `mask` is the number's last four digits. A server with Postgres and no `BUDGET_TOKEN_KEY` refuses OFX and QFX (422) and still takes CSV. While the ledger's own ids are being upgraded at start, or after that upgrade failed, an OFX or QFX import is a 503 ("try again after a restart"); CSV imports carry on. Import labels (`ImportRecord.label`, the file name) and the report's warnings and notes keep only the last four digits of any run of six or more.

|---|---|---|---|
| GET | `/dash/maintenance/statement-ids` | — | Dashboard only. `{accounts, rows, rules, chats, labels, importsOpen}`: what the start-up upgrade would still rename (counts only). Non-zero only on a server started with `BUDGET_STATEMENT_ID_MIGRATION=audit` (which counts, logs and serves this but changes nothing, and keeps OFX imports off), or one whose upgrade failed; a normal start upgrades before it serves |

### Accounts: PATCH

The person's own corrections to an account (server 0.6.0, `ServerStatus.accountEditsSince`). `Account` carries three optional fields, absent until the person sets them, so older apps and stored ledgers decode unchanged: `nickname` (names the account everywhere: `displayName` is `nickname ?? name`, and `shortLabel`, rule descriptions, the CSV export, Upcoming, Net worth and the dashboard use it, while the bank's `name` keeps updating underneath), `kindSetByPerson` (a provider's guess corrected; SimpleFIN never says what kind an account is) and `maskSetByPerson` (a sync no longer replaces those last digits). A sync never changes an existing account's kind.

| Method | Path | Body | Returns |
|---|---|---|---|
| PATCH | `/v1/accounts/{id}` | `AccountChange {kind?, nickname?, mask?}` | `AccountChangeResult {account, warning?, sentToReview}`. On both listeners: the phone with its token, the dashboard with its header. The id is one path segment, percent-encoded when it needs to be. A field left out stays as it is; an empty `nickname` or `mask` clears it (a cleared mask takes the provider's digits again from the next sync). `nickname` is one line (inner whitespace becomes one space), at most 60 characters, with no control characters and no run of six or more digits (an account number); `mask` is 2 to 5 digits. Sending `kind`, even unchanged, marks it as the person's. A kind change pairs old matched transfers again (card-to-card never pairs; re-pairing only adds pairs, so one this change made card-to-card stays paired, and pairs aren't undone if the kind is changed back), and making an account a card sends its money in filed as Income, but not by the person or a rule, back to review; `sentToReview` counts those rows, and they aren't sent back if the kind is changed again. `warning` says what to check: a card with a positive balance (signs are never flipped). Undo is a second PATCH with the previous values (the dashboard sends `mask: ""` for digits the provider set, so they stay the provider's; a kind, once sent, stays marked as the person's). 404 for an unknown account; 422 for a nickname or digits it won't keep, changing nothing |

### Duplicates and merges

Server 0.6.0 (`ServerStatus.possibleDuplicatesSince`). An incoming row is compared with rows already on the account from another source, same amount within 5 days (`Deduplicator.decide`). One that qualifies is a match and the incoming row is skipped, as before. With two or more, it's a match only when the best wording is near-identical (similarity ≥ 0.8) or clearly ahead of the next (by more than 0.25); otherwise it's **ambiguous**: the row is added, not dropped on a guess, and waits in review even if a rule filed it, with a reason naming the row it might be (old apps see it in the normal review queue). Answering its category on the phone means "keep it". The after-the-fact sweep (`POST /v1/imports/duplicates`) leaves ambiguous rows alone and counts them in `DuplicateSweep.ambiguous`; it doesn't add them to the look-alike list, because a Keep both answer isn't stored and every later sweep would ask again. `IngestReport` gains `possibleDuplicates` (rows added and flagged), `duplicatesSkippedBefore` (of `duplicatesSkipped`, rows an earlier import already skipped, merged or swept: they're logged once, under that import) and `namesImproved` (rows a provider sent again with a newer description, merchant or category hint: taken unless the person renamed the merchant, which keeps their name and updates only "what the bank calls it"; the category is never changed).

Every row skipped as already here, every statement copy the sweep removed, and every Same charge answer goes in the **merge log** (`RowMergeRecord {id, kind: skippedIncoming | sweptFileCopy | duplicateResolved | pendingSettled | pendingDropped, at, batchID?, keptID?, droppedID, dropped, keptBefore?, undoneAt?}`), with both ids and a full copy of what went. Entry ids are `<kind>-<batch>-<n>`, never the row id. A row the person merged with Same charge, or a statement copy the sweep removed, stays gone when the same statement or sync sends it again (counted in `duplicatesSkipped` and `duplicatesSkippedBefore`); Bring back is the way to have it back. Entries are kept 400 days. On Postgres it's the `budget_merges` table (migration 5), not a ledger document.

**Stale pending rows (window sources).** A SimpleFIN pull has no "removed" list: a pending row that posts under a new id, or that the bank drops, just stops coming. After each account's rows, an ingest sweeps that account's pending rows when the snapshot asked for pending rows (`SourceSnapshot.includesPending`) and the account came through without an error with `SourceAccount.coveredFrom` set. Plaid (it sends removals), statement files, accounts not in the pull and rows within 2 days of `coveredFrom` are never swept. A missing pending row is **settled** into a new posted row of the same sign dated 1 day before to 10 days after it, whose wording agrees (similarity ≥ 0.5) and whose amount fits: 75% to 130% + $2 of the hold, any amount for a hold of $1.50 or less with near-identical wording (a fuel pump), or less than the hold (but at least 25% of it) with near-identical wording. Pairs are one to one: when two posted rows fit one pending row, or two pending rows one posted row, nothing settles. A pending row that no new posted row fits can settle into a posted row already in the ledger (same account, dated on the pending row's day up to 10 days after, not already a settled row's): a bank can list the pending and posted rows together for a pull or two. A settled row's note, tags, hidden and renamed merchant go to the posted row, and so does its category when the person set it (or it was one side of a transfer, whose pairing moves too). Otherwise a missing row is remembered (`LedgerState.pendingMisses`, a `budget_docs` document on Postgres) and **dropped** when it's missing again 12 hours or more later; a row seen again is forgotten. Both go in the merge log (`pendingSettled` with both ids, `pendingDropped` with no `keptID`) and come back with Bring back; a row brought back isn't dropped again, or settled again into a row already here. Undoing a sync batch (`DELETE /v1/imports/:batch`) first puts back the pending rows that batch settled or dropped, and any settled into a row the batch added, and drops those log entries, so they settle again into the posted row the next sync re-sends; the rollback plan's message says so. `IngestReport` gains `pendingSettled` and `pendingDropped` (optional), and a `notes` line says what happened. Known limit: a pending row settles only into a posted row, so if a bridge re-issues a still-pending charge under a new id, the old row is dropped by the miss rule and its edits stay in the log (whether SimpleFIN does this is unverified).

|---|---|---|---|

| POST | `/v1/duplicates/{id}` | `{sameAs: "<row id>" \| null}` | `{merged: RowMergeRecord \| null}`. On both listeners. `null` (Keep both) clears the question; the row stays in review for its category. ## Rules the server owns

- **All math.** Totals, comparisons, percentages in insight text, and projections are computed by the ledger. `AskReply.figures` must be tool outputs, never model-generated numbers.
- **Review threshold.** `Categorization.needsReview` is set by the server's confidence policy. The client never re-derives it.
- **Model routing.** Each job runs the model picked for it on the dashboard ([models](#models-server-051)). In `ServerStatus.roles`, `chat` and `plan` name the chat model in use, and `categorize` the local decision model (`clef`) whenever the picked categorizing server has an address, whatever the policy's provider. There are no role evals yet (`evalsPassed` is always false), and `discoveredModels` is always empty. The app only displays this.
- **Privacy.** Raw rows never leave the Olares. `rawDataStaysLocal` lets the app surface a violation.

## Client behavior

- `CachingBudgetAPI` stores the last good response for each read (Caches directory, complete file protection). When the server is unreachable, it serves that copy and flips the privacy badge to "Offline copy". Writes and questions are never cached.
- The unfiltered first page of transactions, goal-less projections, rules, merchant memory, each budget month, each category history, the scenario list and each month's flow are cached (a projection against a scenario isn't); searches, other pages, summaries, goal checks, action previews and Sync now always hit the server. Offline, `transaction(id:)` finds the row in the cached page when it's there. Each server's copies are kept apart (`ResponseCache.appDefault(for:)`, a folder per host and port), so a phone moved to another server never shows the old one's numbers. A screen's first load in a session shows its saved copy (`SavedCopies.saved(_:as:)`) at once and refreshes it in place, the privacy badge reading "Updating" until the fresh answer lands or the request gives up (then "Offline copy").
